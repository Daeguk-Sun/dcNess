# 결정 완전성 기준 — 실제 작업 회고 검사

## 이 문서에서 확인할 것

이 문서는 새 작업이나 eval을 실행하는 절차가 아니다. 결정 완전성 기준을 이미 작성된 실제 작업 두 건에 소급 적용한 회고 검사다.

실제 운영에서는 `/spec` 최종화 전과 `/design` 최종 검증 때 같은 기준을 사용한다. 여기서는 기준이 불필요한 질문을 늘리지 않으면서 중요한 미결정을 찾는지만 확인한다.

확인할 질문은 두 가지다.

1. 이미 문서나 목표에서 답을 찾을 수 있는데도 사람에게 불필요하게 질문하지 않았는가?
2. 답에 따라 구현 방향이 달라지는 중요한 선택은 빠짐없이 드러냈는가?

각 회고 검사에는 쉬운 요약을 먼저 적고, 원본 추적에 필요한 시각과 해시는 맨 아래 **출처 검증 정보**로 분리했다.

## Pilot A — 실제 세로 영상 제작 목표를 회고한 샘플

### 한눈에 보기

이 샘플은 실제 프로젝트에서 “자막 없는 짧은 클립을 일관된 스타일의 완성 세로 영상으로 만든다”는 목표를 구현 전에 다시 읽은 결과다. 하네스 자체의 eval이나 운영 비용은 검토 대상이 아니다.

- 이미 정해진 것: 입력은 미리 잘라온 클립이고, 별도 편집기는 만들지 않으며, 완성 출력과 업로드 기본 정책이 명세에 적혀 있다.
- 구현 전에 더 확인해야 하는 것: 유료 합성 음성 서비스의 실제 사용 가능성·비용·상업 사용 조건과 무료 대체 경로가 제품 약속을 충분히 지키는지 명세에 근거가 없다.
- 질문 관찰: 이미 정해진 입력·출력·업로드 정책은 다시 묻지 않고, 오디오 대체 경로에 관한 중요한 질문 한 건만 드러냈다.

### 구현 방향을 바꾸는 선택

1. **입력은 미리 잘라온 자막 없는 클립이며 별도 편집기는 만들지 않는다.**
   - 근거 상태: **사용자 확정**
   - 이유: 승인된 목표가 제품 범위를 클립 인테이크부터 완성 출력까지로 제한한다.
   - 명세 또는 수용 기준 연결: 업로드한 클립에서 자막 초안을 만들고 교정 결과를 최종 렌더에 반영하는 기준으로 이어진다.

2. **사용자가 자동 생성된 자막을 교정한 뒤 그 결과를 최종 영상에 반영한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 제품 수용 기준이 자동 초안을 그대로 확정하지 않고 사용자 교정을 제품 흐름에 포함한다.
   - 명세 또는 수용 기준 연결: 자막 text와 timing 교정이 실제 최종 출력에 반영돼야 한다.

3. **같은 템플릿은 서로 다른 클립에서도 같은 스타일을 만든다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 반복 제작에서 일관된 화면 구성이 핵심 제품 약속이다.
   - 명세 또는 수용 기준 연결: 서로 다른 두 출력의 글꼴·위치·색이 같아야 한다.

4. **템플릿 내부 구현 세부는 제품 경계를 지키는 범위에서 구현자가 정한다.**
   - 근거 상태: **명시적 위임**
   - 이유: 프리셋 선택·저장·재선택과 화면 일관성은 고정됐지만 내부 저장 표현과 구성 방식은 제품 동작을 바꾸지 않는 구현 세부다.
   - 명세 또는 수용 기준 연결: 저장 후 다시 선택할 수 있고 동일 템플릿 결과가 일관되면 된다.

5. **완성 영상은 세로 규격으로 내보내고 공개 전 검토 가능한 상태로 업로드한다.**
   - 근거 상태: **사용자 확정**
   - 이유: 출력 규격과 보수적인 업로드 기본값이 승인된 제품 정책에 적혀 있다.
   - 명세 또는 수용 기준 연결: 완성 파일 규격과 업로드 상태를 실제 동작으로 확인한다.

6. **유료 합성 음성 서비스와 대체 경로가 제품 약속을 지킬 수 있는지 확인한다.**
   - 근거 상태: **미결정 처리**
   - 이유: 명세는 기술 검토가 끝났다고 하지만 실제 작업 계획에는 비용·상업 사용 조건이 있는 외부 서비스와 무료 대체 경로가 새로 등장한다.
   - 명세 또는 수용 기준 연결: 실제 사용 가능성·비용·사용 조건·대체 품질을 기술 검토로 확인하고, 결과에 따라 오디오 수용 기준이나 범위를 보강해야 한다.

Story 분할과 첫 end-to-end 동작이 늦게 나오는 문제는 별도의 Story 순서 검수 항목이다. 결정 완전성 질문과 섞어 같은 근거로 세지 않는다.

### 사람이 답할 질문

이미 명세에 있는 입력·출력 정책을 다시 질문하지 않고, 구현을 실제로 바꿀 수 있는 합성 음성 의존성 한 건을 추가 확인 대상으로 잡은 것이 적절한가?

- 현재 상태: **human verification 대기**
- 동의하면: `Pilot A 회고 승인`
- 빠진 선택이 있으면: 어떤 선택이 왜 구현을 바꾸는지만 적는다.

## Pilot B — Epic 마감 코드 감사를 회고한 샘플

### 한눈에 보기

이 작업은 Epic이 끝날 때 오래된 경로, 의미 없는 테스트, warning 같은 잔존물을 독립 검수하는 방법을 정한다.

- 새로 물어볼 필요가 없었던 것: 기존 검수자의 역할, read-only 권한, coverage 해석은 현재 구조와 측정 정확도 원칙에서 확인할 수 있었다.
- 이번 확인에서 새로 드러난 것: build-worker가 이미 실행한 test·lint·build를 메인이 항상 다시 실행할 필요가 있는지는 결정되지 않았다.
- 상황이 생기면 물어봐야 하는 것: framework에서만 쓰이는 코드인지, 다음 작업을 위한 의도적 seam인지 근거가 없을 때는 삭제하지 않고 소유자에게 되돌린다.
- 질문 관찰: 중복 실행 정책은 비용과 최종 증거 신뢰도를 바꾸므로 사람 결정을 받아야 한다.

### 구현 방향을 바꾸는 선택

1. **새 검수자를 만들지 않고 기존 read-only 구현 검수자를 재사용한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 기존 검수자가 이미 구현자와 분리돼 있고 코드 품질과 테스트 신뢰도를 판단한다.
   - 명세 또는 수용 기준 연결: 새 공개 surface 없이 내부 감사 mode로 동작해야 한다.

2. **최종 Epic 후보의 test·lint·build 증거를 어떻게 확보할지 정한다.**
   - 근거 상태: **미결정 처리**
   - 이미 하는 일: build-worker는 각 task에서 필요한 test·lint·build를 실행한다.
   - 메인이 추가로 필요한 경우: 여러 task가 합쳐진 최종 code revision과 증거의 revision이 다르거나, 감사 범위가 더 넓거나, warning·coverage 정보가 빠졌을 때다.
   - 선택 A — **재사용 우선(권장)**: build-worker 증거가 최종 revision과 필요한 범위를 덮으면 재사용하고, 메인은 빠졌거나 stale한 검사만 실행한다.
   - 선택 B — **항상 재실행**: Epic 마지막에 같은 명령을 전부 다시 실행한다. 최종 후보의 단일 증거는 얻지만 시간과 비용이 중복된다.
   - 명세 또는 수용 기준 연결: 선택 결과를 Codebase Sanity의 기계적 증거 수집 계약에 반영해야 한다. read-only 검수자는 어느 쪽이든 전달된 증거만 판정한다.

3. **coverage 도구나 report가 없으면 `UNKNOWN`으로 남긴다.**
   - 근거 상태: **목표에서 도출**
   - 이유: test 개수를 coverage로 추정하면 잘못된 clean 판정이 된다.
   - 명세 또는 수용 기준 연결: receipt에 측정 불가 근거를 그대로 남긴다.

4. **작은 저장소는 전체를, 큰 저장소는 영향 범위를 중심으로 감사한다.**
   - 근거 상태: **명시적 위임**
   - 이유: 저장소 규모에 맞춰 비용을 조절하되 실제 감사 범위는 반드시 보고하게 했다.
   - 명세 또는 수용 기준 연결: receipt에 code revision과 감사 scope를 기록한다.

5. **도달 가능성이나 보존 이유가 불명확한 코드는 자동 삭제하지 않는다.**
   - 근거 상태: **미결정 처리**
   - 이유: framework 진입점이나 다음 작업의 seam일 수 있다.
   - 명세 또는 수용 기준 연결: unknown/escalate로 분류해 재작업 또는 소유자 판단에 연결한다.

### 사람이 답할 질문

먼저 중복 실행 정책을 선택해야 한다.

- `Pilot B 선택 A` — 같은 최종 revision·범위를 덮는 build-worker 증거는 재사용하고 부족한 것만 메인이 실행
- `Pilot B 선택 B` — Epic 마지막에 메인이 test·lint·build를 항상 전부 재실행

그 뒤 위 다섯 선택이면 새 검수자 추가 여부, coverage 해석, 잘못된 코드 삭제 위험을 정하기에 충분한지 확인한다.

- 현재 상태: **human verification 대기**
- 선택까지 포함해 동의하면: `Pilot B 선택 A 승인` 또는 `Pilot B 선택 B 승인`
- 빠진 선택이 있으면: 어떤 선택이 왜 구현을 바꾸는지만 적는다.
