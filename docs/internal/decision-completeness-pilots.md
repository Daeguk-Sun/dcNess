# 결정 완전성 pilot — 사람 확인용 요약

## 이 문서에서 확인할 것

아래 실제 작업 두 건을 다시 살펴봤다. 확인할 질문은 딱 두 가지다.

1. 이미 문서나 목표에서 답을 찾을 수 있는데도 사람에게 불필요하게 질문하지 않았는가?
2. 답에 따라 구현 방향이 달라지는 중요한 선택은 빠짐없이 드러냈는가?

각 pilot에는 먼저 쉬운 요약을 적고, 원본 추적에 필요한 시각과 해시는 맨 아래 **출처 검증 정보**로 분리했다.

## Pilot A — 제품 결과를 어떻게 증명할지 정한 작업

### 한눈에 보기

이 작업은 “프로세스가 잘 돌았다”는 기록과 “사용자가 실제로 원하는 결과를 얻었다”는 증거를 분리해 측정한다.

- 새로 물어볼 필요가 없었던 것: 비용 상한, 첫 검증 범위, 측정 목적은 이미 작업 목표에 적혀 있었다.
- 사람에게 남겨야 했던 것: 실제 UI 증거가 사용자 관점에서 충분한지는 결과물이 나온 뒤 사람이 봐야 한다.
- 질문 관찰: 기존 근거로 네 선택을 닫았고, 지금 당장 답할 추가 질문은 만들지 않았다.

### 구현 방향을 바꾸는 선택

1. **과정 지표와 실제 제품 결과를 분리한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 기존 측정만으로는 사용자가 실제 journey를 성공했는지 알 수 없다.
   - 명세 또는 수용 기준 연결: 결과 측정에 별도 분모와 공개 evidence를 요구한다.

2. **추가 언어모델 trial은 월 최대 4회로 제한한다.**
   - 근거 상태: **사용자 확정**
   - 이유: 개인 개발자가 감당할 비용 상한으로 이미 승인됐다.
   - 명세 또는 수용 기준 연결: ablation 기록과 월간 누계에서 확인한다.

3. **첫 검증은 non-UI 1건과 UI 또는 실제 사용자 흐름 1건으로 제한한다.**
   - 근거 상태: **목표에서 도출**
   - 이유: 서로 다른 제품 경계를 확인하면서 범용 플랫폼 구축으로 커지는 것을 막는 최소 범위다.
   - 명세 또는 수용 기준 연결: 두 journey의 실제 실행 증거로 확인한다.

4. **첫 ablation의 구체 후보는 실행자가 고른다.**
   - 근거 상태: **명시적 위임**
   - 이유: 반복 비용이 확인된 선택형 구성요소 안에서만 고른다는 경계가 이미 있다.
   - 명세 또는 수용 기준 연결: 선택 이유와 keep/remove/hold 결과를 기록한다.

5. **UI 증거가 사람에게 충분한지는 자동 결정하지 않는다.**
   - 근거 상태: **미결정 처리**
   - 이유: 실제 결과물이 생기기 전에는 판단할 수 없다.
   - 명세 또는 수용 기준 연결: 사람 확인 안내에 남겨 최종 소유자가 판단한다.

### 사람이 답할 질문

위 다섯 선택이면 구현 방향을 정하기에 충분하고, 지금 단계에서 불필요한 추가 질문이 없다고 보는가?

- 현재 상태: **human verification 대기**
- 동의하면: `Pilot A 승인`
- 빠진 선택이 있으면: 어떤 선택이 왜 구현을 바꾸는지만 적는다.

## Pilot B — Epic 마감 때 코드베이스를 감사하는 작업

### 한눈에 보기

이 작업은 Epic이 끝날 때 오래된 경로, 의미 없는 테스트, warning 같은 잔존물을 독립 검수하는 방법을 정한다.

- 새로 물어볼 필요가 없었던 것: 기존 검수자의 역할, read-only 권한, coverage 해석은 현재 구조와 측정 정확도 원칙에서 확인할 수 있었다.
- 상황이 생기면 물어봐야 하는 것: framework에서만 쓰이는 코드인지, 다음 작업을 위한 의도적 seam인지 근거가 없을 때는 삭제하지 않고 소유자에게 되돌린다.
- 질문 관찰: 기존 근거로 네 선택을 닫았고, 실제 reachability 근거가 없는 경우만 나중 질문 대상으로 남겼다.

### 구현 방향을 바꾸는 선택

1. **새 검수자를 만들지 않고 기존 read-only 구현 검수자를 재사용한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 기존 검수자가 이미 구현자와 분리돼 있고 코드 품질과 테스트 신뢰도를 판단한다.
   - 명세 또는 수용 기준 연결: 새 공개 surface 없이 내부 감사 mode로 동작해야 한다.

2. **test·lint·build·coverage 명령은 메인 workflow가 실행한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: read-only 검수자에게 실행·쓰기 권한을 추가하지 않기 위해서다.
   - 명세 또는 수용 기준 연결: 검수자는 전달된 실행 증거만 의미 판정한다.

3. **coverage 도구나 report가 없으면 `UNKNOWN`으로 남긴다.**
   - 근거 상태: **목표에서 도출**
   - 이유: test 개수를 coverage로 추정하면 잘못된 clean 판정이 된다.
   - 명세 또는 수용 기준 연결: receipt에 측정 불가 근거를 그대로 남긴다.

4. **작은 저장소는 전체를, 큰 저장소는 영향 범위를 중심으로 감사한다.**
   - 근거 상태: **명시적 위임**
   - 이유: 저장소 규모에 맞춰 비용을 조절하되 실제 감사 범위는 반드시 보고하게 했다.
   - 명세 또는 수용 기준 연결: receipt에 code revision과 감사 scope를 기록한다.

5. **도달 가능성이나 보존 이유가 불명확한 코드는 자동 삭제하지 않는다.**
   - 근거 상태: **미결정 처리**
   - 이유: framework 진입점이나 다음 작업의 seam일 수 있다.
   - 명세 또는 수용 기준 연결: unknown/escalate로 분류해 재작업 또는 소유자 판단에 연결한다.

### 사람이 답할 질문

위 다섯 선택이면 새 검수자 추가 여부, coverage 해석, 잘못된 코드 삭제 위험을 정하기에 충분하고 불필요한 질문은 없다고 보는가?

- 현재 상태: **human verification 대기**
- 동의하면: `Pilot B 승인`
- 빠진 선택이 있으면: 어떤 선택이 왜 구현을 바꾸는지만 적는다.
