# 결정 완전성 기준 — 실제 작업 회고 검사

## 이 문서에서 확인할 것

이 문서는 새 작업이나 eval을 실행하는 절차가 아니다. 결정 완전성 기준을 이미 작성된 실제 작업 두 건에 소급 적용한 회고 검사다.

실제 운영에서는 `/spec` 최종화 전과 `/design` 최종 검증 때 같은 기준을 사용한다. 여기서는 기준이 불필요한 질문을 늘리지 않으면서 중요한 미결정을 찾는지만 확인한다.

확인할 질문은 두 가지다.

1. 이미 문서나 목표에서 답을 찾을 수 있는데도 사람에게 불필요하게 질문하지 않았는가?
2. 답에 따라 구현 방향이 달라지는 중요한 선택은 빠짐없이 드러냈는가?

각 회고 검사에는 쉬운 요약을 먼저 적고, 원본 추적에 필요한 시각과 해시는 맨 아래 **출처 검증 정보**로 분리했다.

## Pilot A — 실제 세로 영상 제작 목표를 회고한 샘플

### 한눈에 보기

이 샘플은 실제 프로젝트에서 “자막 없는 짧은 클립을 일관된 스타일의 완성 세로 영상으로 만든다”는 목표를 구현 전에 다시 읽은 결과다. 하네스 자체의 eval이나 운영 비용은 검토 대상이 아니다.

- 이미 정해진 것: 입력은 미리 잘라온 클립이고, 별도 편집기는 만들지 않으며, 완성 출력과 업로드 기본 정책이 명세에 적혀 있다.
- 구현 전에 더 확인해야 하는 것: 유료 합성 음성 서비스의 실제 사용 가능성·비용·상업 사용 조건과 무료 대체 경로가 제품 약속을 충분히 지키는지 명세에 근거가 없다.
- 질문 관찰: 이미 정해진 입력·출력·업로드 정책은 다시 묻지 않고, 오디오 대체 경로에 관한 중요한 질문 한 건만 드러냈다.

### 구현 방향을 바꾸는 선택

1. **입력은 미리 잘라온 자막 없는 클립이며 별도 편집기는 만들지 않는다.**
   - 근거 상태: **사용자 확정**
   - 이유: 승인된 목표가 제품 범위를 클립 인테이크부터 완성 출력까지로 제한한다.
   - 명세 또는 수용 기준 연결: 업로드한 클립에서 자막 초안을 만들고 교정 결과를 최종 렌더에 반영하는 기준으로 이어진다.

2. **사용자가 자동 생성된 자막을 교정한 뒤 그 결과를 최종 영상에 반영한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 제품 수용 기준이 자동 초안을 그대로 확정하지 않고 사용자 교정을 제품 흐름에 포함한다.
   - 명세 또는 수용 기준 연결: 자막 text와 timing 교정이 실제 최종 출력에 반영돼야 한다.

3. **같은 템플릿은 서로 다른 클립에서도 같은 스타일을 만든다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 반복 제작에서 일관된 화면 구성이 핵심 제품 약속이다.
   - 명세 또는 수용 기준 연결: 서로 다른 두 출력의 글꼴·위치·색이 같아야 한다.

4. **템플릿 내부 구현 세부는 제품 경계를 지키는 범위에서 구현자가 정한다.**
   - 근거 상태: **명시적 위임**
   - 이유: 프리셋 선택·저장·재선택과 화면 일관성은 고정됐지만 내부 저장 표현과 구성 방식은 제품 동작을 바꾸지 않는 구현 세부다.
   - 명세 또는 수용 기준 연결: 저장 후 다시 선택할 수 있고 동일 템플릿 결과가 일관되면 된다.

5. **완성 영상은 세로 규격으로 내보내고 공개 전 검토 가능한 상태로 업로드한다.**
   - 근거 상태: **사용자 확정**
   - 이유: 출력 규격과 보수적인 업로드 기본값이 승인된 제품 정책에 적혀 있다.
   - 명세 또는 수용 기준 연결: 완성 파일 규격과 업로드 상태를 실제 동작으로 확인한다.

6. **유료 합성 음성 서비스와 대체 경로가 제품 약속을 지킬 수 있는지 확인한다.**
   - 근거 상태: **미결정 처리**
   - 이유: 명세는 기술 검토가 끝났다고 하지만 실제 작업 계획에는 비용·상업 사용 조건이 있는 외부 서비스와 무료 대체 경로가 새로 등장한다.
   - 명세 또는 수용 기준 연결: 실제 사용 가능성·비용·사용 조건·대체 품질을 기술 검토로 확인하고, 결과에 따라 오디오 수용 기준이나 범위를 보강해야 한다.

Story 분할과 첫 end-to-end 동작이 늦게 나오는 문제는 별도의 Story 순서 검수 항목이다. 결정 완전성 질문과 섞어 같은 근거로 세지 않는다.

### 사람이 답할 질문

이미 명세에 있는 입력·출력 정책을 다시 질문하지 않고, 구현을 실제로 바꿀 수 있는 합성 음성 의존성 한 건을 추가 확인 대상으로 잡은 것이 적절한가?

- 현재 상태: **human verification 승인 (2026-07-12)**
- 사용자 확인: 합성 음성 의존성 한 건에 질문을 집중한 범위가 적절하다고 승인했다.
- 빠진 선택이 있으면: 어떤 선택이 왜 구현을 바꾸는지만 적는다.

## Pilot B — 실제 기본 메시지 앱 목표를 회고한 샘플

### 한눈에 보기

이 샘플은 실제 외부 프로젝트에서 “기기의 기본 메시지 앱으로 기존 대화를 이어 보고 문자를 송수신한다”는 목표를 구현 전에 다시 읽은 결과다. 하네스 자체의 검수 절차나 코드 품질 감사는 검토 대상이 아니다.

- 이미 정해진 것: 개인 사용자·단일 회선 범위, 시스템 메시지 저장소와 재생성 가능한 로컬 미러의 관계, 발신 상태와 재전송, 기본 앱이 아닐 때의 read-only 동작, 권한 거부와 데이터 보호 정책이 명세에 적혀 있다.
- 구현 전에 더 확인해야 했던 것: 새 메시지를 처음 보낸 뒤 별도 대화 화면으로 이동할지, 같은 화면이 대화 상태로 전환될지는 초기 명세만으로 정해지지 않았다.
- 질문 관찰: 이미 정해진 데이터·권한·복구 정책은 다시 묻지 않고, 화면 구조와 입력 연속성을 바꾸는 사용자 경험 선택 한 건만 드러냈다.

### 구현 방향을 바꾸는 선택

1. **개인 사용자 한 명이 단일 회선에서 기존 문자 이력을 이어서 사용한다.**
   - 근거 상태: **사용자 확정**
   - 이유: 승인된 범위가 다중 회선·다중 사용자를 후속으로 미루고 기본 메시지 송수신에 집중한다.
   - 명세 또는 수용 기준 연결: 기본 앱 지정, 기존 대화 표시, 송수신과 알림의 actor·범위를 제한한다.

2. **시스템 메시지 저장소를 진본으로 두고 앱의 로컬 저장소는 재생성 가능한 읽기 미러로 사용한다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 설치 전 이력과 외부 변경을 함께 보여 주려면 하나의 진본에서 다시 수렴해야 하며, 승인된 명세와 데이터 결정이 같은 관계를 사용한다.
   - 명세 또는 수용 기준 연결: 기존 메시지 전량 표시, 변경 감지 후 화면 반영, 소스가 달라도 identity가 충돌하지 않는 기준으로 이어진다.

3. **발신 메시지는 전송 중에서 전송됨 또는 실패로 전이하고, 실패한 본문은 다시 보낼 수 있다.**
   - 근거 상태: **프로젝트 근거**
   - 이유: 제품 명세가 사용자에게 보이는 상태와 실패 복구를 이미 정의한다.
   - 명세 또는 수용 기준 연결: 같은 메시지 버블의 상태 변화, 실패 표시, 재전송 동작 기준으로 이어진다.

4. **백그라운드에서 알림 권한이 없으면 메시지는 보존하고, 다음 foreground에서 권한을 요청한다.**
   - 근거 상태: **목표에서 도출**
   - 이유: 백그라운드 수신 주체는 권한 창을 직접 열 수 없지만, 승인된 정책은 권한 거부가 알림만 막고 메시지 반영은 유지하도록 한다. 따라서 권한 필요 신호를 보존했다가 사용자가 앱을 다시 볼 때 요청하는 경로가 두 제약을 함께 만족한다.
   - 명세 또는 수용 기준 연결: 권한이 없을 때 해당 동작만 막는 기준과, 수신 메시지가 목록·상세에는 계속 반영되는 기준으로 이어진다.

5. **아바타 플레이스홀더의 구체 표현과 내부 화면 구성 세부는 제품 경계를 지키는 범위에서 구현자가 정한다.**
   - 근거 상태: **명시적 위임**
   - 이유: 번호 기반 구분과 빈 상태·상태 표시라는 사용자 약속은 고정됐지만, 제네릭 도형·이니셜 표현과 내부 컴포넌트 분리는 결과를 바꾸지 않는 세부다.
   - 명세 또는 수용 기준 연결: 각 대화에 구분 가능한 플레이스홀더가 보이면 된다.

6. **새 메시지 첫 발신은 별도 화면으로 이동하지 않고 같은 화면이 대화 상태로 전환한다.**
   - 근거 상태: **미결정 처리**
   - 발견 당시 상태: 초기 명세는 “발신 후 대화 상세로 이동한다”만 적어 별도 작성 화면을 없애는 전환과 같은 화면 안 상태 전환을 구분하지 않았다. 초기 설계는 별도 화면 이동을 근거 없이 채웠다.
   - 처리 결과: 사용자가 입력 연속성을 보존하는 같은 화면 전환을 확정했고, 별도 작성 화면·교체 navigation을 제거하는 설계 결정으로 반영됐다.
   - 명세 또는 수용 기준 연결: 새 메시지 발신 기준을 “화면 전환 없이 받는 사람 입력이 대화 헤더로 바뀌고 전송 중 버블이 같은 화면에 나타난다”로 구체화해 구현·관찰 기준에 연결했다.

### 사람이 답할 질문

이미 정해진 actor·데이터·권한·실패 복구를 다시 질문하지 않고, 실제로 화면 모듈과 navigation을 바꾼 첫 발신 전이 한 건만 사용자 선택 대상으로 잡은 것이 적절한가?

- 현재 상태: **human verification 승인 (2026-07-12)**
- 사용자 확인: 첫 발신 화면 전이 한 건에 질문을 집중한 범위가 적절하다고 승인했다.
- 빠진 선택이 있으면: 어떤 선택이 왜 구현을 바꾸는지만 적는다.
