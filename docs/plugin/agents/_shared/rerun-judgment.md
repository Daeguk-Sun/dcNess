# 재실행 범위와 반복 중단 판단

검증·검수·수렴처럼 같은 대상을 다시 실행하거나 다시 검토하는 agent 와 그 agent 를 호출하는 메인이 함께 쓰는 판단 기준이다. harness 가 강제하는 것은 순서(코드 리뷰 통과 → 같은 커밋에서 제품 검수 통과)뿐이다. 무엇을 다시 할지와 언제 멈출지는 고정 조건이 아니라, 변경분과 실행 기록을 읽은 agent 가 정한다.

아래는 형식이 아니라 의미 요구다. 표·heading·고정 문구를 요구하지 않는다.

## 다시 할 범위를 고른다

대상은 journey, 시나리오, 설계 산출물, 검토 항목, 수용 기준처럼 한 번 통과 판정을 받은 단위다.

1. **변경분을 읽고 고른다.** 직전 통과 판정 이후의 변경분을 읽고, 그 변경이 닿을 수 있는 대상만 다시 실행·검토한다.
2. **스스로 전체로 올린다.** 영향이 넓거나 불확실하면 agent 가 전체 범위로 올린다. 호출자는 범위를 좁혀 처방하지 않고, 전체로 올리는 것도 막지 않는다.
3. **다시 하지 않은 이유를 적는다.** 다시 하지 않은 대상마다 "왜 이 변경이 닿지 않는가"를 결과에 적는다.
4. **기록이 없으면 전체로 한다.** 직전 통과 기록이 없거나 변경분을 계산할 수 없으면 전체 범위로 수행한다.

### 통과 기록이 근거가 되는 조건

통과 기록은 그 대상의 **가장 최근 결과**일 때만 생략의 근거가 된다.

- 통과한 뒤에 같은 대상이 실패했거나 gap 으로 남은 기록이 있으면, 그 통과는 더 이상 현재 상태를 말하지 않는다. 전체 실행과 부분 실행의 실패, 직전 검증·검수의 FAIL 을 모두 그 대상의 결과로 읽는다.
- 실패하거나 gap 으로 남은 대상은 변경분이 닿는지와 무관하게 생략 후보가 아니다. 다시 실행·검토해 해소를 확인하거나 gap 으로 유지한다. 같은 커밋에서 실패한 대상을 "변경이 없다"는 이유로 건너뛰지 않는다.
- 앱 미기동, 준비 확인 실패, 정리 실패처럼 특정 대상에 묶이지 않는 실패가 통과 뒤에 있으면 그 실행이 다루던 모든 대상의 통과 기록을 근거로 쓰지 않는다.

### 변경이 닿는지 읽는 법

파일 경로 규칙으로 판정하지 않는다. 변경된 내용이 대상이 실제로 지나는 경로에 들어가는지를 읽는다.

- journey·시나리오라면 그 흐름이 지나는 화면, 진입점, 상태, 데이터, 그 흐름의 대본과 실행 배관이 경로다.
- 설계 산출물이라면 그 산출물이 인용하거나 의존하는 계약, 상태, 화면, 결정, 다른 task 가 경로다.
- 수용 기준이라면 그 기준을 관찰하는 명령과 그 명령이 실행하는 코드가 경로다.
- 빌드 설정, 의존성, 공유 모듈, 공통 테스트 배관, 전역 결정의 변경은 닿는 범위가 넓다. 닿지 않는다는 근거를 댈 수 없으면 전체로 올린다.
- 문서만 바뀐 변경은 실행되는 제품 경로에 닿지 않는다. 다만 그 문서가 다른 설계 산출물의 근거이면 그 산출물에는 닿는다.

"닿지 않는다"는 판단은 근거를 댈 수 있을 때만 한다. 근거 없이 "아마 무관하다"로 생략하지 않는다. 다시 실행하지 않은 대상이 뒤에 실패한 사례가 실제로 있으므로, 생략은 비용을 줄이는 대신 위험을 진다는 점을 저울에 올린다.

### journey 실행 기록에서 읽는 사실

[`product-journey.md`의 판단 재료](../../product-journey.md#다시-실행할지-판단하는-재료)가 다음을 제공한다.

- receipt 의 `code_revision`: 그 실행의 커밋이다. 통과한 receipt 의 커밋과 현재 HEAD 사이의 diff 가 "직전 통과 이후의 변경분"이다.
- receipt 의 `uncommitted_changes`: `true` 이면 그 실행은 커밋되지 않은 변경을 포함했다. 커밋 diff 만으로는 변경분을 다 읽지 못한다.
- `skip` 기록: journey 나 시나리오를 다시 실행하지 않기로 했으면 이유와 함께 남긴다. 나중에 그 판단이 맞았는지 확인하는 유일한 자료다. 도구는 근거로 삼을 통과 receipt 뒤에 그 대상의 미해소 실패가 있으면 근거가 없다고 출력한다. 이 출력이 나오면 생략하지 않는다.

부분 실행 receipt 와 `skip` 기록은 전체 실행 receipt 가 아니다. Epic 결과 요약과 outcome scorecard 는 전체 실행 receipt 만 센다. 가장 최근 전체 실행 receipt 가 실패인 journey 는 부분 재실행이 통과해도 집계에서 실패로 남는다. 그 journey 의 통과를 집계에 남겨야 하면 전체 실행이 필요하다는 점을 범위 판단에 넣는다.

## 반복을 멈출지 판단한다

실행 → 관찰 → 수정 → 재실행, 또는 검증 실패 → 보강 → 재검증을 반복하는 agent 와 메인은 횟수를 세어 멈추지 않는다. 매번 다음을 판단한다.

- **다시 실행하기 전에 답한다.** "이번 실행은 직전 실행과 무엇이 다르고, 어떤 관찰이 나오면 내 가설이 맞거나 틀린가." 답이 없으면 다시 실행하지 않는다.
- **같은 신호가 다시 나오면 신호를 먼저 의심한다.** 수정한 뒤에도 같은 실패 신호가 나오면 수정 대상보다 신호 자체를 먼저 확인한다. 검사 도구의 오판, 실행 환경, 제품 결함 순서로 본다.
- **더 싼 관찰을 먼저 쓴다.** 전체 실행 전에 화면 캡처, 화면 구조 조회, 시나리오 하나만 실행, 명령 직접 실행처럼 싼 관찰로 가설을 확인한다.
- **기록이 원인을 담지 않으면 관찰 수단부터 보강한다.** 실행 log 가 원인을 담지 않는데 같은 실행을 반복하면 같은 빈 기록만 늘어난다.
- **새 정보가 없으면 멈춘다.** 새 정보가 더 나오지 않거나 누적 비용이 얻는 정보보다 크다고 판단하면 멈추고 사용자에게 보고한다.
- **서로 다른 실패의 순차 노출은 진전이다.** 실패 하나를 고치자 다음 실패가 드러나는 것은 멈출 이유가 아니다. 이 경우에도 누적 비용은 계속 본다.

journey 실행 도구는 실행마다 같은 journey 의 누적 실행 횟수, 누적 시간, 연속 실패, 직전 실행과 실패 신호가 같은지를 출력한다. 이 출력의 "같은 신호"는 원인이 같다는 뜻이 아니라 관찰이 구분되지 않는다는 뜻이다.

### 설계·기획 구간의 재시도

검증 실패 → 산출물 보강 → 재검증에도 같은 기준을 쓴다.

- 같은 영역의 지적이 수렴하는지 읽는다. 지적이 줄거나 좁아지면 진전이다.
- 수렴하지 않으면 점 수정으로 다시 돌리지 않는다. 그 영역의 근본 원인을 다시 검토하거나 사용자에게 보고한다.
- **분류만 바꿔 계속 재시도하지 않는다.** 지적의 분류, 영역, 파일, 지적 수, 검증 provider 가 바뀌었다는 사실은 새 시도의 근거가 아니다. 과거에 이 구분이 흐려져 같은 검증이 여러 번 자동으로 다시 돌았다. 새 지적이 나왔다는 것과 설계가 수렴한다는 것은 다른 사실이다.

### 멈출 때의 보고

멈추면 사용자에게 다음을 알린다. 문장 형식은 자유다.

- 시도한 것과 각 시도에서 바꾼 것
- 관측한 신호와 그 신호가 반복됐는지
- 남은 가설과 각 가설을 확인하는 데 드는 비용
- 누적 실행 횟수와 시간
- 고를 수 있는 선택지(계속, 범위 분리, 상위 단계 재진입, 보류)

## 강제하지 않는 것

- 이 문서는 hook 이나 도구가 차단하는 규칙이 아니다. 순서 강제는 [`hooks.md`](../../hooks.md)가 소유하고 이 문서는 그 순서를 바꾸지 않는다.
- 검수 agent 는 새 커밋에서 계속 호출된다. 호출된 agent 가 실제로 무엇을 다시 실행할지 정한다.
- 숫자 한도를 중단 조건으로 쓰지 않는다. 횟수와 시간은 판단에 쓰는 사실이지 자동 차단선이 아니다.
