# Spec PRD Reference

`/spec` 내부 구현 절차가 PRD 초안을 만들 때 쓰는 참고 자료다. 진행 순서와 분기는 [`SKILL.md`](SKILL.md) 와 [`spec-routing.md`](spec-routing.md) 가 진본이다.

## 그릴미 패턴

메인은 `/grill-me` 원문 지시를 번역 없이 그대로 적용한다.

> Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one-by-one. For each question, provide your recommended answer.
>
> Ask the questions one at a time.
>
> If a question can be answered by exploring the codebase, explore the codebase instead.

추가 맥락:

- **이해 도달이 1차, PRD 작성은 그 기록** — 목표는 `shared understanding` 도달이고, PRD 산출물 체크리스트는 대화의 부산물이다.
- **입력은 재료이지 진실이 아니다** — 사용자가 가져온 기존 문서나 외부 도구 산출물은 도전 가능한 재료로 취급한다. 문서 존재 자체는 좋은 요구사항의 증거가 아니며, 대화와 사용자 확인을 거친 내용만 PRD 에 확정한다.
- **체크리스트 충족 != 종료** — 핵심 분기에서 사용자가 납득하지 못했으면 빈칸이 다 차도 계속 질문한다. 하류 검수가 있다는 이유로 그릴 대화를 얕게 끝내지 않고, 하류 검수에서 발견되는 gap 은 검수 성공이 아니라 그릴 대화 실패 신호로 본다.
- **객관식 후보보다 자연어 대화** — 메인은 2~3개 선택지를 던져 고르게 하는 방식에 갇히지 않는다. 사용자의 표현을 되묻고, 앞선 답변과 코드 탐색 결과를 연결하며, 맥락을 누적해 다음 질문을 만든다. 권장안은 제시하되 대화 흐름 안에서 합의한다.
- **why 부터, how 로 직행 금지** — 목적, 실제 페인, 규모를 먼저 판다.

### 결정 완전성 의미 계약

아래 예시 관점은 대화를 시작하는 단서이고, 구현 전에 닫아야 할 결정의 전체 의미는 [`decision-completeness.md`](../../docs/plugin/decision-completeness.md)가 소유한다. actor, 데이터와 관계, 상태와 lifecycle, 실패와 복구, 권한과 보안, 외부 연동, 사용자 경험과 정책, 운영 제약 중 작업에 관련된 결정 범위를 본다.

각 중요한 선택은 사용자 확정, 프로젝트 근거, 목표에서 도출한 이유, 낮은 영향의 명시적 위임 중 하나로 닫는다. 근거 없는 가정과 중요한 미결정은 PRD 초안으로 숨기지 않고 질문, 기술 검토 필요 영역, 또는 `/design`에서 닫을 구체적 product boundary로 보낸다. `/design` 후속이라고 적는 것만으로 사용자 정책·데이터 lifecycle·권한처럼 구현 방향을 바꾸는 미결정을 닫았다고 보지 않는다.

이 점검은 고정 questionnaire나 별도 결정 표가 아니다. 질문 개수와 출력 형식을 강제하지 않고, 코드·기존 SSOT에서 확인 가능한 사실을 먼저 읽어 불필요한 질문을 줄인다.

### 핵심 분기 탐색의 예시 관점

아래 네 관점은 흔한 누락을 찾는 예시이지 전수 questionnaire가 아니다. 메인은 작업에 관련된 관점만 탐색하고, 코드·기존 SSOT를 프로젝트에서 확인할 수 있으면 질문하지 않는다. 중요한 선택과 분기 해소 결과는 해당 PRD 기록 위치에 반영한다. 표에 없는 관점이라도 관련 결정 범위이면 확인하고, 표의 관점이라도 작업과 무관하면 `해당 없음` 답변을 받기 위한 질문을 만들지 않는다.

| 질문 축 | 확인할 내용 | PRD 기록 위치 |
|---|---|---|
| 유저 저니·유즈케이스 | 누가 어떤 상황에서 어떤 순서로 가치를 얻는지, 반복 사용과 첫 사용 흐름이 다른지 | 서비스 개요 / 기능별 스펙 / 화면 인벤토리 + 대략적 플로우 |
| 아키텍처 결정 지점 | 선택지의 pros·cons, MVP 한정 결정인지 확장 전제인지, 실패 시 스코프 영향 | 외부 의존 보호 / 기술 검토 필요 영역 / 스코프 결정 |
| 엣지케이스·실패 flow | 잘못된 입력, 빈 상태, 권한 부재, 외부 의존 실패, 복구 가능 여부 | 기능별 스펙의 유저 시나리오 / 화면 인벤토리 + 대략적 플로우 |
| 보안·법적 | 권한, 개인정보, 데이터 보존, 약관·라이선스·규제 위험, 사용자가 알아야 하는 제한 | 보안 · 법적 고려 / 기술 검토 필요 영역 |

아키텍처 결정 지점은 PRD 단계에서 결정 후보와 product 스코프 영향을 식별하는 데까지만 다룬다. 모듈 구조, 인터페이스, 저장소 설계 같은 구체 구조 설계는 `/design` 영역으로 남긴다.

### 종료 기준

초안 작성으로 넘어가기 전 메인은 현재 확인한 **핵심 분기 목록**을 사용자에게 선언한다. 다음 조건이 모두 충족되어야 초안 작성으로 진행한다.

- 작업에 관련된 결정 범위를 프로젝트 근거와 대화에서 식별했다.
- 중요한 선택은 사용자 확정·프로젝트 근거·목표에서 도출한 이유·낮은 영향의 명시적 위임 중 하나로 닫혔다.
- 핵심 분기 목록의 분기 해소 상태가 PRD 기록 위치에 반영됐다.
- 미해결 항목이 있으면 `기술 검토 필요 영역`, `스코프 결정`, 또는 `/design` 후속으로 명시됐고 MVP 진행 가능 여부가 닫혔다.
- [`decision-completeness.md`](../../docs/plugin/decision-completeness.md) 기준으로 구현 방향을 바꿀 근거 없는 가정과 중요한 미결정이 0개다.

### 강도 스케일링

- **신규 PRD** — 작업에 관련된 결정 범위를 폭넓게 탐색한다. 대화 초반에 핵심 분기 목록을 만들고, 질문이나 프로젝트 근거로 분기가 해소되며 목록을 갱신한다.
- **기존 PRD 변경** — 변경이 닿는 영향 범위 한정으로 그릴미를 축소한다. 보안·법적 또는 아키텍처 관점도 변경과 관련될 때만 근거를 확인하며, 프로젝트에서 확인할 수 있는 사실을 다시 묻지 않는다.
- 기존 PRD 변경은 모르는 섹션을 통째로 다시 쓰지 않는다. 필요한 섹션만 patch 하고, 변경하지 않은 구양식 PRD 는 그대로 허용한다.

## PRD 산출물 의무

`docs/prd.md` 는 [`templates/prd.md`](templates/prd.md)를 문서 템플릿으로 작성한다. 템플릿의 9개 섹션이 PRD 산출물 의무다. 메인은 그릴미 대화 중 각 섹션이 실제 맥락으로 채워졌는지 확인한다.

외부 의존 보호 항목은 product 요구사항과 대체 불가 이유를 결과 중심으로 쓴다. "그대로 / 1:1 동등 / 동일하게 / 이식 / port / parity / 마이그레이션 그대로" 같은 HOW 단어가 product 요구사항으로 들어오면 PRD 단계에서 거부한다.

## 기능 나열과 유저 시나리오 작성

PRD 는 제품이 제공할 기능 나열과 유저 시나리오까지 소유한다. 기능별 스펙에는 우선순위, 사용자가 보게 될 동작, 정상·실패·복구 시나리오를 제품 언어로 적는다. `As a / I want / So that` 와 검증 가능한 `Given / When / Then` 약속으로 닫는 작업은 이후 `stories.md` 의 Story AC 가 소유한다.

PRD 에 Story 수용 기준을 두지 않는다. 새 PRD 에 `AC-NNN` 목록이나 별도 수용 기준 섹션을 만들지 않으며, task 실행 명령인 `REQ-NNN` 도 두지 않는다. 이미 머지된 구양식 PRD 의 AC 는 소급 이동하거나 번호를 바꾸지 않고 기존 프로젝트 호환 입력으로만 인정한다.

## 기술 검토 필요 영역 작성 기준

PRD 초안 작성 때 아래 중 하나라도 참이면 `docs/prd.md` 의 **기술 검토 필요 영역**에 검토 질문 / PRD 근거 / 성공·실패 시 PRD 영향을 기록한다. `/tech-review` 실행 여부는 이후 Step 4 에서 이 섹션에 실제 검토 항목이 있는지로만 결정한다. 예외용 "뒤에 둬도 됨" 목록은 두지 않는다.

- 새 외부 API / SDK / model / 라이브러리 도입
- 비용, 라이선스, 성능, 품질이 MVP 성패를 좌우
- "이게 되는지"가 기능 정의 자체를 바꿀 수 있음
